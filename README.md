# opencode-plugin-socks-relay

Плагин OpenCode V2: направляет выбранные хосты через SOCKS5-прокси
(обычно `ssh -D`), а всё остальное пускает напрямую.

## Зачем

На некоторых сетях DPI читает TLS SNI и режет соединения к отдельным доменам
(`taynik.store`, `api.synthetic.new` и т.п.): рукопожатие проходит, а дальше
пакеты теряются и соединение рвётся через ~19 секунд. Если трафик идёт через
SSH-туннель до своего сервера, DPI видит только SSH.

Провайдеры, которые не блокируются, идут напрямую и ничего не теряют.

## Режим router (по умолчанию)

Плагин поднимает локальный HTTP CONNECT-прокси и выставляет для процесса
сервера OpenCode `HTTPS_PROXY`/`HTTP_PROXY`. Дальше OpenCode сам решает, куда
идти: хосты из списка `tunnel` уходят в SOCKS5, все остальные — напрямую.

Плюсы: TLS остаётся end-to-end (прокси только туннелирует), поэтому версия TLS
и размер тела запроса не важны, а провайдеры настраиваются как обычно — их
`baseURL` менять не нужно.

### Настройка

1. Туннель (держать запущенным):

   ```bash
   ssh -N -D 1080 user@your-server
   ```

2. `~/.config/opencode/socks-routes.json`:

   ```json
   {
     "mode": "router",
     "port": 8789,
     "socks": "127.0.0.1:1080",
     "tunnel": ["taynik.store", "api.synthetic.new"]
   }
   ```

3. `opencode.json` — провайдеры остаются со своими обычными адресами:

   ```jsonc
   {
     "providers": {
       "taynik": {
         "package": "@opencode/ai/providers/openai-compatible",
         "settings": { "baseURL": "https://taynik.store/v1" }
       }
     }
   }
   ```

4. `opencode reload` (или перезапуск OpenCode).

### Как выбирается маршрут

- `taynik.store` → в туннель;
- `api.synthetic.new` → в туннель;
- `sub.taynik.store` → тоже в туннель (совпадение по суффиксу);
- всё остальное (`opencode.ai`, `*.aliyuncs.com`, `github.com`, …) → напрямую.

### Что меняется в процессе

- `HTTPS_PROXY=http://127.0.0.1:8789`, `HTTP_PROXY=...`, `NO_PROXY` дополняется
  `localhost,127.0.0.1,::1`.
- Переменные выставляются только в процессе сервера OpenCode; системные
  настройки Windows не меняются.
- Дочерние процессы сервера (shell-инструмент) наследуют эти переменные, но
  для них всё, что не в списке, идёт напрямую.

## Режим relay (legacy)

Локальный origin-сервер с фиксированными апстримами: `baseURL` провайдера
указывает на `http://127.0.0.1:<port>/<name>/v1`. Нужен, если SOCKS нет, а
работает только TLS 1.2.

```json
{
  "mode": "relay",
  "port": 8788,
  "socks": "127.0.0.1:1080",
  "tlsMaxVersion": "TLSv1.2",
  "upstreams": { "taynik": "taynik.store:443", "synthetic": "api.synthetic.new:443" }
}
```

## Проверено

Режим router, тестовый SOCKS5-сервер на этой же машине:

| Проверка | Результат |
|---|---|
| `https://github.com` (в списке tunnel) | ✅ 200, 530 КБ за 284 мс |
| `https://example.com` (нет в списке) | ✅ 200 напрямую, 105 мс |
| `https://api.github.com` (не в списке) | ✅ 200 напрямую |
| Запрос OpenCode к `alibaba-token-plan` | ✅ прошёл напрямую через роутер |
| `https://taynik.store` без запущенного `ssh -D` | ❌ 502 `connect ECONNREFUSED 127.0.0.1:1080` |

## Диагностика

- `GET http://127.0.0.1:8789/__relay/health` — режим, список туннелей, счётчик
  и последние 10 запросов (какой хост и куда ушёл).
- Лог: `%TEMP%\opencode\socks-relay.log`.
- Если релей не может достучаться до SOCKS, будет `502` и запись
  `connect failed for <host>: connect ECONNREFUSED 127.0.0.1:1080` — значит,
  `ssh -D` не запущен или указан другой порт.

## Жизненный цикл

- `setup()` при загрузке плагина: старт прокси и выставление переменных.
- Слушатель живёт до выхода процесса OpenCode; при `opencode reload` новый
  экземпляр переиспользует уже занятый порт (проверка по health), поэтому
  прокси не пропадает.
- Порт освобождается при выходе из OpenCode.
